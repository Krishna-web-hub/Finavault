FinVault docs/architecture

How this is built

A secure, self-hostable multi-agent RAG platform for finance — where the encryption, access-control, and compliance layers are the product, not a wrapper around it.

1Problem analysis

What has to be true for this to work

A finance team needs to ask natural-language questions over sensitive internal documents — filings, compliance policies, client memos — without those documents ever leaking: to unauthorized internal users, to external systems, or via prompt-injection hidden inside the documents themselves.

Functional

  • Ingest .pdf .docx .txt .md .csv, tag each with a sensitivity tier
  • Answer questions grounded in those documents, with citations
  • Viewer / Analyst / Compliance Officer / Admin see different tiers of content
  • Every answer is reviewed before it reaches the user

Non-functional

  • Confidentiality at rest — a compromised DB leaks nothing readable
  • Confidentiality in transit — the most sensitive tier never reaches the LLM at all
  • Non-repudiation — access history can't be silently edited
  • Fail closed — uncertainty defaults to no-answer, never a guess
2High-level architecture

Where a question travels

One browser session, one FastAPI process, and four agent identities coordinating over a shared encrypted store. The Compliance step sits outside the agent's own tool set on purpose — it's Python control flow the model can't opt out of.

3Component breakdown

What each piece is for, and what breaks without it

ComponentPurposeWhat breaks if removedAlternative considered
encryption.py Envelope-encrypts every chunk (AES-256-GCM); each chunk gets its own data key, wrapped by a master key. A compromised Qdrant instance leaks raw text. Per-chunk keys mean one leak exposes one chunk, not the corpus. Single global key — simpler, but one leak is total
access_control.py Maps Role → minimum clearance per Classification tier. Without it, retrieval has no concept of who's allowed to see what. DB-level row security — harder to unit-test centrally
retriever.py Vector search → ACL filter → hybrid rerank (BM25 + vector via reciprocal rank fusion) → optional cross-encoder → decrypt. Unauthorized chunks are dropped silently, not flagged. Flagging "access denied" would leak that a restricted document exists — the silence is the point. Filter at the Qdrant payload-index level
retriever_agent.py Second, independent gate: a chunk outside the externalization allowlist never has its text assembled into a tool result at all. Without this, ACL-cleared restricted content still reaches the LLM provider — proven live before this fix existed. Gate only the final answer — insufficient, found the hard way
orchestrator.py Delegates to Retriever/Analyst via tool calls; routes every draft through Compliance unconditionally. If Compliance were a callable tool instead of hard-coded control flow, a confused model could just skip it. One monolithic agent with every tool
compliance_agent.py Externalization check → regex PII scan/redact → LLM semantic review, in that order. Regex alone misses novel injected instructions; LLM alone is non-deterministic for known-shape secrets. LLM-only review
guardrails.py Delimits retrieved text as data-not-instructions; heuristic injection detector as a second signal. Any ingested document can carry an injected instruction — the delimiter is the primary defense. Rely on model training alone — proven insufficient industry-wide
audit.py Hash-chained, append-only log — each entry's hash depends on the previous one. A raw UPDATE against Postgres, bypassing the app entirely, is detectable — verified live. Plain table with timestamps — tamperable by anyone with DB access
embeddings.py Local sentence-transformers — vectors computed on-device. A cloud embedding API would see every document's raw text just to compute a vector. Voyage/OpenAI embeddings — better quality, second third party sees your data
agents/base.py Generic tool-use loop, zero finance-specific logic — every agent is this loop plus a prompt and tools. Also owns reliability hardening (retry-on-empty-turn, fail-closed on malformed responses) — a property of talking to an LLM, not of finance. A framework like LangChain — less auditable, we wanted every request/response inspectable
ingestion/extraction.py Entity/relationship extraction agent — runs once per document at ingest time, same untrusted-content defense as retrieval. Degrades to an empty result on failure or malformed output; never blocks embed/encrypt/store. Extract per-query from retrieved chunks instead — rejected: re-extracts the same document on every question, no whole-document lineage
retrieval/graph_store.py Envelope-encrypts extracted labels/relations like chunk text; exact-match dedup via an unkeyed label_hash. Plaintext labels in graph_nodes would leak document content the ACL is supposed to gate. Fuzzy entity resolution — deliberately out of scope
retrieval/graph_retriever.py ACL-filtered decrypt for the Knowledge Graph canvas — mirrors retriever.py exactly, down to dropping an edge whose endpoint is hidden. A visible edge pointing at a withheld node would itself leak that the node exists. Filter only on the edge's own classification — insufficient, an endpoint can be more sensitive than the edge
agents/comparison_agent.py Extracts comparable per-document metric values (LLM); _score_variance() then computes each metric's risk score deterministically from those numbers. An LLM-assigned risk score would be ungrounded and non-reproducible — the same pair of figures could score differently between runs. Ask the model for a risk_score field directly — rejected for the same reason AnalystAgent's arithmetic is AST-sandboxed, not LLM-computed
retriever.get_document_text() Reassembles one document's full plaintext from its chunks, in order, after an ACL check — the read path comparison needs but retrieval's top-k search doesn't provide. Comparison would only ever see a handful of semantically-retrieved fragments instead of whole documents. Store plaintext separately for whole-document reads — rejected, a second at-rest copy of content the encryption model exists to avoid
4Execution flow

One /query request, start to finish

  1. 1
    Browser sends question + JWT to POST /query
  2. 2
    FastAPI verifies the JWT and reconstructs User(role, org_id) — never trusts a client-supplied role
  3. 3
    Orchestrator.handle() logs the query, loads session history (compliance-approved turns only), initializes real-time execution step DAG tracing, and runs agent loop
  4. 4
    Orchestrator calls search_documents → RetrieverAgent runs its loop, logging Step 1 (retriever) execution trace
  5. 5
    Each chunk is checked against the externalization allowlist; disallowed chunks become a withheld-notice before ever becoming a tool result
  6. 6
    Orchestrator calls analyze → AnalystAgent produces the answer, logging Step 2 (analyst) — Knowledge Graph entities were already extracted at ingest time, not here
  7. 7
    Orchestrator synthesizes a draft answer
  8. 8
    ComplianceAgent.review_output() runs checks and logs Step 3 (compliance) verdict trace
  9. 9
    Any failed check → blocked, reason logged, generic message returned along with step DAG trace
  10. 10
    All checks pass → clean, returns {answer, citations, execution_steps, graph_data}
  11. 11
    Frontend Visual Workspace renders live updates across 💬 Chat, 🕸️ Knowledge Graph, ⚡ Execution DAG, and 📊 Risk Heatmap
5Technology choices

Why this, not the obvious alternative

ChoiceWhyLimitation
FastAPIAsync-native, Pydantic validation, OpenAPI for freeNo built-in horizontal-scale story beyond multiple processes
QdrantSelf-hostable — stays inside the boundary; payload filtering for org-scoping at query timeEmbeddings can theoretically leak some source-text signal (inversion research) — documented, unsolved
PostgreSQLReal transactions for both the documents table and the hash-chained audit logPostgresAuditLog is correct for single-writer; multi-writer needs an advisory lock
AES-256-GCMAuthenticated encryption — tampered ciphertext fails to decrypt, not "decrypts to garbage"None significant at this scale
OpenAI SDK → OpenRouterAny OpenRouter model — including free ones — is a config change, not a rewriteOne more hop versus calling a provider directly
Canvas Engine & DAG TraceVisual entity mapping & real-time multi-agent execution DAG auditabilityRequires client-side canvas DOM rendering for complex graph layouts
6GenAI pipeline

Only the stages that are actually earning their place

StageWhat's usedWhy (or why not)
ChunkingParagraph-aware, fixed size + overlapDeterministic, no LLM call needed
Embeddingssentence-transformers · bge-small, localKeeps this step inside the boundary — see §3
Vector DBQdrant, org-scoped filter + cosine similaritySelf-hostable, filters at query time
RetrievalTop-k → ACL filter → externalization filter → hybrid rerank (BM25 + optional cross-encoder via RRF) → decryptTwo independent security gates, not one; reranking runs only over already-authorized, decrypted candidates
Knowledge GraphExtractionAgent at ingest time → encrypted graph_store.pyExtraction is once per document, not per query; canonical normalization fuzzy entity resolution merges variations (e.g. Inc, LLC, Corp) into unified entity nodes; graph_data on /query is scoped to retrieved documents, and GET /graph serves the full org graph on demand
Risk HeatmapComparisonAgent on demand → POST /documents/compareMetric values are LLM-extracted per document; the risk score is computed deterministically from those numbers, never asked of the model
Execution TracingLive DAG Step Auditor in orchestrator.pyTracks sub-agent execution flow (Retriever → Analyst → Compliance) with execution timing and payload previews
Agent reasoning4-agent split — route / retrieve / reason / veto; per-session memory (compliance-approved turns only)Independently testable units, not one do-everything prompt; history never includes blocked turns
Output generationOrchestrator's synthesis, always Compliance-reviewedRaw model output never reaches the caller unchecked
7Knowledge check

Five questions before we go further

  1. Why are ACL clearance and externalization policy two separate checks instead of one? Sketch a scenario where a user passes one but should still fail the other.
  2. If the AAD binding in encryption.py — the piece tying ciphertext to document_id:chunk_index — were removed, what specific attack becomes possible that wasn't before?
  3. The Compliance agent's semantic review is itself an LLM call. What happens if that call fails or returns something malformed — and why isn't the fallback "assume it's fine"?
  4. Why hash-chain the audit log instead of a plain table with created_at? What attacker does chaining defend against that a timestamp doesn't?
  5. We chose to silently drop chunks a user isn't cleared for over telling them access was denied. What's the security reasoning — and what UX cost does that tradeoff have?
